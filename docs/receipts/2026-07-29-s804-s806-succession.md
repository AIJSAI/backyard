# S-804 + S-806 — the instance can be handed on, shut down, or watched

Two stories, built together because **S-804 depended on something that did not exist.**

## The finding that reordered the work

S-804's fourth acceptance line reads *"…and the health email reports domain
days-remaining."* There was **no health email**. No code, no template, no task — and **no
story** either. Threat row **T-MON-1** is rated **High**:

> *"Nothing is watching: a dead backup cron or a filling disk goes unnoticed for months,
> giving every other threat unlimited dwell time."*

Its stated mitigation was entirely unbuilt, and a story referenced it as though shipped. So
S-806 was proposed and built first.

Of the five fields T-MON-1 names, only **one** was computable from existing data:

| field | before |
|---|---|
| last-backup age | **nothing recorded that a backup had ever run** — a dead cron was indistinguishable from a healthy one |
| disk headroom | computable |
| domain days-remaining | needed an outbound lookup that did not exist |
| failed sign-ins | no auth audit log exists |
| off-box backup age | **not knowable by the app at all** |

## S-806 — the health email

**The load-bearing rule is the negative one.** A field with no instrumentation is reported
as `NOT MEASURED`, never omitted. An email that silently drops a signal it cannot compute
reads as *"everything is fine"* — which is precisely the T-MON-1 failure, wearing a
feature's costume. Two fields say so on every send, and say *why*, naming the threat row so
a reader can tell which parts of "nothing is watching" are still true.

What it looks like on a bare instance:

```
This is the weekly health check for backyard.family. Nothing here needs doing unless a
line is marked [!].

[!] Last backup: NEVER — no backup has completed on this instance
    Disk headroom: 75% free (696.9 GB)
[!] Domain: backyard.family expires in 355 days
    Failed sign-ins: NOT MEASURED — no auth audit log exists yet (T-MON-1)
    Off-box backup age: NOT MEASURED — the instance cannot see where you copied a backup
                        to (T-OP-G3); check it yourself
```

- **`BackupRun`** records completed backups — written *after* the rename and the decrypt
  check, never on entry, because a row written on entry makes a crashed or undecryptable
  backup look successful and the email would then reassure an operator about a backup that
  does not exist. A failure to record never fails the backup itself.
- **`DomainStatus`** caches the RDAP expiry, refreshed on the **worker** (S-725 / TS-CO-4:
  the edge process makes no outbound connections) and **keeping its last good value** when a
  lookup fails, so a registry outage degrades one field rather than silencing the one message
  an operator most needs. A check older than 14 days is labelled stale rather than passed off
  as current.
- **`NEVER` is distinct from `NOT MEASURED`** — conflating "no backup has ever run" with
  "cannot tell" would hide the worse case behind the milder word.
- Recipients mirror the digest's rule exactly (instance admin, confirmed address). The
  consequence is real: an admin who never confirmed one gets nothing, and then nobody is
  watching. So `send_health_emails` **reports** having sent none and the task logs a warning,
  rather than returning quietly — and both runbooks tell the new admin to confirm.

### Two real bugs the tests caught

- A backup taken seconds earlier rendered as **"-1 days ago"**: `auto_now_add` stamps from
  the database clock, which can sit microseconds after the caller's `now`.
- **Disk headroom died outright** when `MEDIA_ROOT` did not exist yet — and because that
  path is `alarming`, a perfectly healthy instance shouted. Headroom is a property of the
  *volume*, so it now walks up to the nearest existing ancestor.

### Live, not mocked

Real RDAP against the real domain: **`backyard.family` expires 2027-07-20**, resolved in
0.26s through a redirect to `rdap.identitydigital.services`. A **transient timeout** during
an earlier run accidentally demonstrated the graceful degradation working exactly as
designed — the field read `NOT MEASURED — no successful lookup yet` and the email still
sent.

## S-804 — handover, shutdown, succession

**The order is the safety property**, and it is not the intuitive one:

```
1. EXPORT   for at least two named members
2. REVOKE   every credential, while the box is still up
3. DESTROY  volumes and provider snapshots — by hand, not by this command
```

Export first, because a shutdown that revoked and *then* failed to export would have
destroyed access to data nobody held a copy of. Revoke while the box still answers, because
every printed QR points at your hostname and a bearer URL cannot tell your host from the
next one — skip it and the first thing those links meet is whoever re-registers the domain
(**T-OP-G4**).

Step 3 is deliberately **not** automated: destroying a provider snapshot needs credentials
this process has no business holding, and *"the command deleted the snapshots before I had
checked the export"* is not a recoverable mistake. It prints the steps and refuses to
pretend it did them.

Revocation is `backups.revoke_every_credential` — the **same implementation a restore
uses**. Two implementations of "kill every credential" is how one of them comes to miss a
class, and that is pinned by a test.

### Driven live, as an operator would

| attempt | result |
|---|---|
| no `--confirm` | refused; **nothing written** |
| one custodian | refused — "one custodian is the bus factor this procedure exists to remove" |
| the same name twice | refused (the obvious way to satisfy a two-name check by accident) |
| a name that does not exist | refused; **nothing written**, no credential touched |
| an ambiguous name | refused rather than guessing |
| the real run | 2 exports written, **both open clean** (Priya 2 posts + 3 media; Sam 1 post + 1 comment), 6 members rotated, and an elder link minted beforehand **no longer resolves** |

### The documents

- **`handover.md`** — the accounts, then every secret rotated in an order that keeps the app
  serving, then every token regenerated *and elder links re-issued* (or the grandparents are
  locked out with no way to ask), then the domain, then confirming the health email reaches
  the new person, then removing the outgoing person's access **last**. Ends with a short
  section for the case where you are reading it because someone died.
- **`shutdown.md`** — the three-step order, the one command, and the four things it will not
  do for you. The domain goes **last and slowest**, because printed QR codes are in kitchen
  drawers.
- **`backup-recovery-sheet.md`** is now a **succession sheet**: second admin, registrar and
  renewal date, host account, email provider, and where the off-box copy lives. A passphrase
  with no note of who else can reach the server recovers the files and loses the instance
  anyway.
- **`self-host.md`** treats the domain as a family asset at registration time — auto-renew,
  multi-year, registrar lock, two people on the account.
