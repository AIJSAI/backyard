{% load i18n %}{% comment %} PROJECT OVERRIDE of django-allauth's account/messages/password_changed.txt.

   It exists to SUPPRESS the message on one flow and to leave it exactly as it was on the
   other, and the split is the whole point of the file.

   What the 2026-09-19 walk saw: finish a password reset from the emailed link and the page
   reads "Password successfully changed." in the green message strip, and then, directly
   underneath, "Your new password is saved. You can sign in with it now." The same fact,
   twice, in two voices, on a page somebody reaches while they are locked out and least able
   to shrug off software that talks to itself. The strip is rendered by core/base.html
   ABOVE the page body, so it is read first — the library's sentence is the one that greets
   them, and the product's own is the echo.

   Why it cannot be suppressed from the page that shows it: allauth adds the message during
   the POST that sets the password (allauth.account.internal.flows.password_reset
   .finalize_password_reset) and then redirects, and core/base.html renders the message
   region before `{{ block.super }}`-style inheritance ever reaches the leaf's content. By
   the time password_reset_from_key_done.html renders, the sentence is already on the page.
   The message is BUILT from this template, so this is the layer where it can be declined.
   The adapter drops a message whose template renders empty (`if escaped_message:` in
   AccountAdapter.add_message), which is what the branch below does.

   Why the branch, and not simply an empty file: allauth raises this ONE message from TWO
   flows. The other is the signed-in password CHANGE (finalize_password_change), where the
   view redirects back to the same form and the message is the ONLY confirmation that
   anything happened — core/base.html's own comment on the message region names that as the
   case it exists for. Emptying this template outright would trade a duplicated sentence on
   one page for a silent success on another, which is the worse defect of the two. So the
   reset flow declines it and every other caller gets the library's sentence unchanged,
   still translated, byte for byte what that surface showed yesterday.

   `resolver_match` is the request that is setting the password: the reset-from-key view.
   If there is no request at all (a management command, say) the lookup resolves to the
   empty string, the branch is taken, and the message is raised — the safe direction, since
   a message too many is a duplicated sentence and a message too few is silence.
